## 0. 阅读须知：`games` 是什么，以及状态图例该怎么读

### 0.1 `games` 是**当前版本的离线本地服务**

需求文档里的 ✅/🟡/🆕 都是相对后端 `games` 判定的。这里必须先把 `games` 的身份说清楚：

> `games` 是《狂欢斗地主》**当前版本的离线本地服务**（Go + Gin + ent + PG + Redis + WS，
> 50+ 端点、203 个 Go 文件、14 个 ent schema）。它服务两个目的：
> **(1) 开发阶段的游戏测试；(2) 未来的离线模式。**
>
> 因此它**不是**"另一个项目/外部平台"，而是**这条产品线自己的另一半**：
> 客户端将来要能同时对接「离线本地服务」和「线上服务」，
> 两者共同实现同一份契约。

**客户端已并入本仓库**：`apps/client/`（Godot 4）。
契约文档就在 [`../../apps/client/docs/`](../../apps/client/docs/)，
因此契约 diff 不再需要跨仓库拷贝（原先的快照副本已删除，见
[`../contract/README.md`](../contract/README.md)）。

> **关于 `games` 的真实形态（重要）**：它**不是**一个独立的 Go 后端，
> 而是**散落在客户端 Godot 代码里的那套本地数据/业务逻辑** ——
> 存档仓库（`profile_repository.gd`）、玩家档案（`player_profile.gd`）、
> 目录表（`game_mode.gd` / `skin_catalog.gd` / `activity_catalog.gd`）、
> 规则引擎（`game_engine.gd` 等），加上 `AppViewModel` 里的报名/结算/购买/签到规则。
>
> 所以"复用 `games`"的真实含义是：**把客户端里已有的这套本地逻辑整理成一个有边界的离线服务**。
> 这件事必须在后端开工前做 —— 见开发计划 **D-16** 与 **C0 阶段**。

本项目 `carnival-landlords` 是**线上服务端**。它与 `games` 技术栈同源
（Gin + ent + PostgreSQL + Redis + WebSocket），但域模型、路径命名、响应信封、
错误码、WS 协议目前是各写一套 —— **这正是本计划要收敛掉的东西**。

### 0.2 状态图例 = **契约成熟度**，不是"和我们无关"

既然 `games` 是同一产品线的离线服务，那三个图例就有了明确含义：

| 图例 | 在离线服务中的状态 | **对本项目（线上服务）的含义** |
| --- | --- | --- |
| ✅（10 条） | 已有可用实现 | **客户端已经按这个形状联调过、离线模式下正在用** → 线上服务应**逐字段对齐**，否则客户端要为两端写分支 |
| 🟡（11 条） | 已有但有已知缺陷 | 形状存在，但 §10.3 记了 5 处真实缺陷 → 线上服务**不要复制这些缺陷**；同时要确认"改好之后离线端怎么办"（见 §0.3） |
| 🆕（105 条） | 缺失 | 全新，可自由设计 |

> **由此得出最重要的一个结论**：契约对齐（信封 `body`、错误码分段、路径命名、WS 协议）
> 不再只是"让客户端好写"的体验优化，而是**双端可切换的前提**。
> 客户端一套网络层要同时打两个 Base URL，契约必须完全一致。
> 这直接抬高了开发计划里 D-01/D-02/D-03/D-08 四项决策的优先级 —— 它们是**阻断级**的。

### 0.3 离线模式是**产品常态**，不是过渡态

需求文档的 Phase 1 把"本地 AI 对局 + 服务端结算"当作临时方案。但既然离线模式是
长期产品形态，本计划需要多考虑两件在"纯线上"假设下不会考虑的事：

| 事项 | 为什么重要 |
| --- | --- |
| **离线期间的进度如何回到线上** | 玩家离线打了几局、签了到、领了任务，联网后这些进度必须能补上（`REC-06` 因此从"可选"升级为**必做**，且要防伪造） |
| **同一份契约，两处实现** | 离线服务的缺陷（如 WS 广播串消息、客户端传金额）如果在线上被"修好"，两端的**行为差异**必须对客户端透明 —— 否则同一份客户端代码在两种模式下表现不一致 |

### 0.4 §10.3 那 12 条"已知问题"的正确读法

它们不是"别人家的问题"，而是**离线服务里真实存在、且客户端可能已经绕着写的缺陷**。
逐条自查结论见本文件 §7.3。对本计划的直接含义：

- 其中 **5 条本项目已经解决**（客户端传金额、签到逻辑、WS 串消息、WS 回显、无流水/无幂等）
  → 线上服务必须**守住**这些，不能为了"和离线端一致"而退回去；
- 另外 **2 条两端都有**（排行榜维度、实名防沉迷）→ 属于共同待办；
- 剩下的（云存档缺字段、profile 缺资产）→ 属于"离线服务的缺陷清单"，
  需要在双端契约评审时一起处理。

### 0.5 好消息

本项目**已经实现了需求 Phase 1 + Phase 2 的大部分核心能力**
（钱包账本、服务端权威对局、匹配、签到、每日任务、商城发货、邮件、排行榜），
缺的主要是**契约形状对齐**、**房间/准备态子系统**、**社交域**、**配置版本化与后台 CRUD**
以及**离线↔在线进度同步**。逐条差距见 [`development-plan.md`](./development-plan.md) 第 2 节。

### 0.6 ID 口径：全链路 ULID（已定）

游戏客户端**所有实体 ID 都是 ULID**（`src/core/ulid.gd`），本项目服务端也一律使用 ULID：

- 服务端生成的**实体 ID**全部是 ULID；
- 服务端接受的实体 ID 参数一律按 ULID 校验；
- **不采用**需求文档提到的"21 位服务端 ID"，也**不需要**独立的 8 位短号分配机制；
- 客户端界面要显示的"ID/短号"由 **ULID 前 8 位**派生
  （与客户端原有 `short_id()` 实现一致），属于展示层派生值，不占独立唯一键。

**客户端的校验是严格的**：`Ulid.is_valid()` 只认「长度恰好 26」+「每个字符都在
Crockford 字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ` 内」（不含 `_`）。
本项目服务端目前有 **31 处**用 `id.NewPrefixed()` 生成了 `<prefix>_<ulid>`
（长度 31、含下划线，如 `room_01M467379Y24XRTAQA9829NWSM`）→ **过不了客户端校验**。
机器人座位 ID（`bot_` + 20 字符）同样如此。
修法与逐项清单见开发计划 **D-04**。

**一个必须区分的例外**：`mode_classic` / `table_classic` / `item_hint_pack` / `gold_100k`
这类是**编译期固定的配置目录键**，客户端与需求文档都用它们，
**它们本来就不是 ULID，也不应该改成 ULID**。

### 0.7 离线产出口径：**只产出少量积分，不产出金币**（已定）

| 币种 | 来源 | 说明 |
| --- | --- | --- |
| **金币 `gold`** | **只有联机模式产出**：线上对局结算、签到、每日任务、成就、比赛奖励、商城礼包 | **离线一克都不产出**。金币因此保持**单币制** |
| **钻石 `diamond`** | 充值（当前为模拟通道）、比赛场奖励、任务/签到奖励 | 不变 |
| **积分 `points`** | 线上对局结算 **+ 离线对局（少量，有每日上限）** | 用于排行榜与匹配分池 |

**关键约束**：

- 离线产出**只有积分**，所以「离线刷金币」这个套利通道**在定义上就不存在** ——
  不需要绑定金币、不需要双币余额、不需要按币种分层结算。
- `points` 有两个消费者，必须区分对待：
  - **排行榜** → 读 `points`（离线积分可参与，对离线玩家是正向激励）；
  - **匹配分池** → 读 `points - offline_points`，**离线积分不计入**，
    否则离线刷积分会让玩家匹配到远高于自身水平的对手。
- 每日上限走配置 `offline.points_daily_cap`，建议按"离线 3~5 局 ≈ 一局线上对局的积分"起步。
- `REC-06` 因此只需做两件事：写**离线战绩** + 累加**少量积分**；
  **不产出金币**，也不推进任务/成就/签到（见 §3.7）。

详见开发计划 **D-15**。

### 0.8 联机/离线怎么切换：**用户无感，默认联机**（已定）

这是本项目在需求文档之上的**产品增强** —— 需求文档是按"未来全面联网"写的，
没有"模式切换"这个概念。

| 项 | 约定 |
| --- | --- |
| 入口 | **系统设置**里一个「联机 / 离线」开关 |
| 默认值 | **联机**（未设置时） |
| 切换体验 | **无感**：不要求重新登录（靠 `game_token`）、不要求重启（服务实现运行时热替换）、不丢当前界面状态 |
| 切到联机时 | **自动同步积分**（上报离线待同步队列），并**开放**商店、任务、签到、成就、排行榜、邮件等联网功能 |
| 切到离线时 | 上述功能**置灰**；已拥有的资产（如已购皮肤）**仍可离线使用** |
| 切换失败 | 提示"当前无法联机，已使用离线模式"，**停留在离线实现**，界面照常可用（绝不清空数据或卡在加载中） |
| 开关存在哪 | **纯本地设置**（设备级），**不参与 `PUT /user/settings` 同步**。<br>硬约束：离线时读不到服务端，若把"是否联机"存在服务端，离线启动就无法判断该不该联机 |
| **前置条件** | **必须已登录**（D-18 取消游客）：没有本地有效凭据时，"离线"选项**不可用**并提示"请先联网登录"。<br>凭据过期仍可继续离线游玩，但**切回联机时要求重新登录** |
| 能力原则 | **已拥有的资产可离线使用；任何消耗或产出的动作必须联机。** |
| 离线与金币 | 离线**不产出也不消耗**金币 —— 否则等于把金币的**扣减权**交给本地权威。离线对局只按局数给少量积分，金币显示上次同步的**只读快照** |

完整的能力矩阵（对局 / 积分 / 金币 / 商店 / 任务 / 排行榜 / 邮件 / 皮肤 / 好友 / 战绩 / 设置
各自在离线与联机下的可用性）见开发计划 **D-17**。

详见开发计划 **D-17** 与 **C0-8**。

## 2. 横向契约要求（必须一次性冻结，否则每条接口都要返工）

这一节是需求文档 §2 的整理。这些是"横向"要求：它们不增加端点，但决定所有端点的形状。
**必须先冻结再写接口**，否则改一处要动全部 handler + 客户端网络层。

### 2.1 接入点

| 项 | 需求约定 | 本项目现状 |
| --- | --- | --- |
| HTTP Base | `https://<host>/api/v1`（开发 `http://localhost:8080/api/v1`） | **一致** |
| WebSocket | `wss://<host>/api/v1/ws/game`（社交/通知继续用 `/api/v1/ws`） | 本项目为 `/api/v1/game/ws`，**需改路径** |
| 认证头 | `Authorization: Bearer <access_token>`；WS 建立后**首帧**发 `auth` | 头一致；WS 现在是 `?token=` 查询串，**需加首帧 auth** |
| 内容类型 | `application/json; charset=utf-8`；上传走 multipart 或 OSS 预签名 | JSON 一致；上传尚未涉及 |

### 2.2 认证与会话

- **Token 三件套**：`access_token`（短期）+ `refresh_token`（长期）+ `game_token`。
  - 需求建议 access 15min~2h、refresh 7d~30d。本项目现为 access 24h / refresh 30d。
    access 24h 是**为了对局期间的稳定性**刻意放宽的；若按需求收紧到 2h，
    必须配合"WS 长连接不因 access 过期而断开"的策略（本项目会话存 Redis，
    WS 鉴权后不再校验 access，因此**可以安全收紧**）。→ 待决策，见计划 D-05。
- **`game_token`**：需求描述为"平台侧识别用户的长期凭证，只允许服务端之间使用"。
  它的真实归属是**离线本地服务**（`games` 有游戏目录 / launch / verify 这套东西，
  因为它同时承担"本地游戏库"的角色）。线上服务是否需要它，
  取决于"客户端是否要求从本地服务启动后无缝切到线上"。
  → 决策见计划 **D-09**。注意：无论结论如何，**`/auth/verify` 的契约形状**建议保留，
  避免客户端出现"同一个流程两端路径不同"。
- **游客账号（已取消）**：需求 `POST /auth/guest`，用 `device_id` 创建/复用游客账号，
  后续可绑定手机/密码升级为正式账号。
  **本项目不实现（D-18）——这是一处对需求 P0 项的主动覆盖。**
  决策：**删除游客登录策略，即便离线游玩也必须是注册并登录过的用户**，
  即不存在"没有服务端账号的玩家"。`device_id` 不再作为账号标识（仍用于会话/设备绑定）。
  - 需求 §2.2 特别强调"客户端旧版本『昵称即账号、无密码』的体验不能直接丢弃"，
    并据此建议新增 `POST /auth/guest`。**该建议被产品推翻**，理由是
    不希望存在游离于账号体系之外的玩家数据。回写说明属 S0 交付项。
  - **代价**：首次使用必须联网注册或登录；**找回密码（AUTH-09/10）从 P1 提到 P0** ——
    无游客兜底后它是唯一的账号救援路径。
  - **收益**：游客→正式的升级/合并、游客资产冲突、孤儿账号清理这几类最容易出错的问题**一并消失**。
- **登录失败**：需要限流 / 锁定，且连续失败返回统一错误以避免账号枚举。
  本项目已做"统一错误文案 + 恒定时间比较"，但**没有失败计数与锁定**。
  取消游客后这条更关键 —— 登录是唯一入口。

### 2.3 响应信封（**最高优先级的契约差异**）

需求：

```json
{ "code": 0, "message": "ok", "body": { } }
{ "code": 10003, "message": "unauthorized" }
```

本项目现状：

```json
{ "code": 0, "message": "ok", "body": { }, "request_id": "01J..." }
```

差异：字段名 `body` vs `data`。另外需求 §7.5 又明确要求
"统一 `request_id` 贯穿 HTTP / WS / 异步任务"，因此 `request_id` 要**保留**。

→ 建议：把 `data` 改名为 `body`，保留 `request_id`。成本极低（一个 JSON tag + 文档），
详见计划 D-01。

→ **已实施（D-01）**：`response.Envelope` 的字段与 JSON tag 已改为 `Body` / `body`，
冒烟脚本与 `docs/api.md` 同步改名。

→ **续（同一决策）**：WebSocket 帧的消息体字段也一并从 `data` 统一为 `body`
（`realtime.ServerMessage.Body`、`game.Event.Body`，以及 `apps/client/docs/` 下
契约文件里的 WS 信封示例）。因此**本服务的 HTTP 与 WS 用的是同一个字段名**，
不再存在"两套协议各叫各的"。

> 与需求原文的差异：需求侧的 WS 信封写的是 `data`（见第 4.2 节），
> 这里按"一个概念一个名字"统一成了 `body`。客户端当时还没有任何 WS 代码，
> 是唯一无痛统一的时刻。Go 结构体名仍是 `*Data`（如 `HandStartData`），
> 那只是类型名，与字段名无关。

### 2.4 错误码（**第二高优先级的契约差异**）

需求建议新增 `8xxxx` 段（28 条），例如：

| Code | 含义 | HTTP |
| --- | --- | --- |
| 80001 | 金币不足 | 400 |
| 80002 | 钻石不足 | 400 |
| 80003 | 余额版本冲突 | 409 |
| 80004 | 重复请求（幂等命中） | 409 |
| 81001~81005 | 房间不存在/已满/密码错/不在房间/状态不允许 | 404/409/403/404/409 |
| 82001~82007 | 不在对局/未轮到/牌型非法/打不过/无此牌/已结束/超时托管 | 404/409/400/400/400/409/409 |
| 83001 | 对局记录不存在 | 404 |
| 84001 / 84002 | 奖励已领取 / 任务未达标 | 409 / 400 |
| 85001 | 配置版本过旧 | 409 |

并要求保留现有 `0 / 10001~10011 / 20001~20003 / 30001~30003 / 40001~40003 /
50001~50003 / 60001~60002 / 70001~70002` 中不冲突的部分。

本项目现状：错误码分段为 `1xxxx 通用 / 2xxxx 认证 / 3xxxx 钱包 / 4xxxx 商城 /
5xxxx 活动 / 6xxxx 对局 / 9xxxx 系统`，与需求的 `8xxxx` 段**语义冲突**
（例如本项目 `60001` 是"房间不存在"，需求是 `81001`）。

→ **决策已改（D-02 结论）**：**不做 `8xxxx` 重排，保留服务端既有分段，
由客户端把码表同步过去。** 客户端尚未落地，此刻同步是零成本的。

理由：`8xxxx` 与服务端已发布的分段语义冲突（同一段数字两边含义不同 ——
服务端 `60001` 是"房间不存在"，`8xxxx` 方案里是 `810xx`）。码值是永久契约，
两套并存只能靠一张翻译表长期维护，是最难维护的形态。

落地方式：
- 服务端新增 `apperr.Catalog()`，导出**权威码表**（`code` / `name` / `message` / `http`）；
- 客户端契约文件 `server-api-catalog.json` 的 `error_codes` 改为该表的 50 条；
- 新增契约测试逐条比对，防止两边漂移；
- 顺手清理了 4 条**永远不会被返回**的死码（`30005` / `40004` / `50005` / `60013`），
  并把只在 mail 包里手工构造的 `50008` 收敛为预定义错误 ——
  表里留着永不触发的码，客户端就会写永不触发的分支。

原 `8xxxx` 提案留档备查（见 `apps/client/docs/server-api-requirements.md` §2.3）。

**连签规则**：昨天签过则 +1；断签从第 1 天重来；满 7 天后下一轮从第 1 天开始。
（与本项目现有实现完全一致。）

**每日任务（4 条，与客户端一致）**：

| task_id | 标题 | 指标 | 目标 | 奖励 |
| --- | --- | --- | --- | --- |
| `task_games` | 完成 3 局对局 | `online_games_today` | 3 | 3000 金币 |
| `task_win` | 获得 1 次胜利 | `wins_today` | 1 | 5000 金币 |
| `task_bomb` | 打出 1 次炸弹 | `bombs_today` | 1 | 5 钻石 |
| `task_streak` | 取得 2 连胜 | `streak_today` | 2 | 8 钻石 |

> **口径已定（D-10）**：
> 1. `task_games` **不限定对局模式**（经典场 / 高倍场 / 癞子场 / 比赛场都算）；
> 2. 但它**只认在线对局** —— 离线模式的对局**不计入任何任务进度**；
> 3. 因此指标名从需求文档写的 `classic_games` 改为 **`online_games_today`**
>    （本项目现有实现 `games_today` 的语义本来就是对的，只需改名）；
> 4. 同理，**签到与成就也只能在线完成** —— 签到必须由线上校验服务端日期后发放
>    （否则改系统时间即可刷奖励），成就的累计指标只在线上结算时推进。

- 指标计数必须由服务端**在在线结算时**累加；跨天自动清零。
- 任务领取要二次校验达标 + 未领取，事务内 `发奖 + 标记已领 + 写流水`。
- 任务 / 签到配置走 §4.4 配置下发，运营后台可改奖励与目标。
- **离线模式不得推进任何任务 / 成就 / 签到进度**（D-10）。客户端在离线模式下
  需要把这三个面板**明确置灰并说明原因**（"需联网完成"），否则玩家会以为是自己操作错了。

## 4. 实时对局协议要求（WebSocket）

### 4.1 连接与认证

```
1. GET wss://<host>/api/v1/ws/game
2. 首帧 { "type": "auth", "request_id": "req-1",
          "payload": { "token": "<access_token>", "client_version": "1.0.3", "platform": "android" } }
3. 服务端回 { "type": "auth.ok",
              "body": { "user_id": "u_xxx", "server_time": 1780000000000, "heartbeat_interval": 25 } }
4. 失败：auth.error + 关闭（close code 1008 / 4001）
```

- 首帧认证超时（5~10s）断开；
- 支持 `auth.refresh` 换新 token，或客户端断线重连；
- 心跳：客户端每 25s 发 `ping`，服务端回 `pong`（服务端也可主动 ping）。

### 4.2 消息信封

```json
{ "type": "game.played", "seq": 1024, "ts": 1780000000000,
  "room_id": "r_xxx", "match_id": "m_xxx", "request_id": "可选", "body": { } }
```

- `seq`：**每个房间/对局单调递增**；客户端发现跳号应主动 `game.sync`。
- `ts`：服务端毫秒时间戳，用于倒计时校准。
- 所有对局事件必须带 `match_id`；房间事件带 `room_id`。

### 4.3 客户端 → 服务端命令（13 条）

`auth`、`ping`、`room.ready`、`room.leave`、`room.chat`、`game.bid`（0~3）、
`game.play`（`card_ids`）、`game.pass`、`game.ready_next`、`game.trustee`（`enabled`）、
`game.sync`（`last_seq?`）、`game.leave`、`match.cancel`。

**服务端必须校验**（需求 §5.8）：

- 是否轮到这个玩家；
- `card_ids` 是否真在该玩家手牌中；
- 牌型是否合法、是否能压过上家；
- 叫分是否在 0~3、是否重复叫分；
- 对局是否已结束；
- 命令频率是否异常（毫秒级连发）。

### 4.4 服务端 → 客户端事件（27 条）

| 分类 | 事件 |
| --- | --- |
| 连接 | `auth.ok`、`auth.error`、`pong` |
| 匹配/房间 | `match.found`、`room.state`、`room.player_joined`、`room.player_left`、`room.ready_changed` |
| 对局主体 | `game.state`、`game.dealt`、`game.bid_turn`、`game.bid_made`、`game.landlord_decided`、`game.turn`、`game.played`、`game.passed`、`game.table_cleared`、`game.multiplier_changed`、`game.player_alarm`、`game.finished`、`game.tournament_update` |
| 连接状态 | `game.player_offline`、`game.player_online`、`game.error` |
| 社交 | `notification`、`friend.invite`、`chat.message` |

### 4.5 快照 `game.state` 与结算 `game.finished`

两份结构的字段清单见原始文档 §5.5 / §5.6。要点：

- 快照必须包含客户端重绘牌桌所需的**全部字段**；未定地主前**不能泄露底牌**，
  未轮到自己**不能泄露他方手牌**（只给 `hand_count`）。
- 快照含 `deadline_ms`、`seq`、`pass_count`、`last_play{seat,cards,pattern}`。
- 结算摘要含 `my_*` 三项（`my_seat`/`my_role`/`my_won`）便于客户端直接渲染，
  以及 `seats[].balance_after` —— **服务端返回的余额才是权威**。
- **三家金币增减之和必须为 0**（平台抽水另计但必须有账务记录）。
- 结算必须由服务端权威状态机完成；结算记录与钱包流水**强一致**。

### 4.6 断线、超时与托管

| 场景 | 要求 |
| --- | --- |
| 客户端断线 | 保留座位与手牌，推 `game.player_offline`，其他人看到离线标记 |
| 重连（如 90s 内） | `GET /rooms/current` → WS `game.sync` → 返回完整 `game.state` |
| 重连超时 | 进入托管由服务端 AI 代打；连续超时/逃跑按规则判负 |
| 操作超时 | 每个 `game.turn` 带 `deadline`；超时自动"不出"或出最小牌 |
| 网络抖动 | 命令带 `request_id`，服务端幂等去重；重复出牌返回同一结果 |
| 服务端重启 | 对局状态建议落 Redis/DB 支持恢复；至少保证已结算对局可查 |

### 4.7 WS 错误码

`4001` 认证失败 / `4002` 重复认证 / `4003` 心跳超时 / `4004` 协议版本不兼容 /
`4101` 房间不存在 / `4102` 房间已满或已开始 / `4103` 不在房间 /
`4201` 不在对局 / `4202` 还没轮到你 / `4203` 牌型不合法 / `4204` 打不过上家 /
`4205` 手牌中没有这些牌 / `4206` 对局已结束 / `4207` 操作超时已托管 /
`4290` 命令过于频繁。

> 注意：这一组 `4xxx` 是 **WS 专用码**，与 HTTP 的 `8xxxx` 是两套编码空间，不要混用。

## 6. 非功能要求

### 6.1 性能与容量（需求标注"待业务确认"）

| 指标 | 目标 |
| --- | --- |
| HTTP 读 P95 | < 200ms |
| HTTP 写 P95 | < 300ms |
| WS 命令确认 P95 | < 100ms（同区域） |
| 出牌广播到其他两端 P95 | < 100ms |
| 快速匹配成功率（含 AI 补位） | > 99%；等待 < 3s 或按配置超时 |
| 同时在线 | 首期按 1 万 CCU 设计，对局服务可水平扩展 |
| 并发房间 | 单实例 1 万房间 / 3 万连接起步 |
| 配置下发 | 启动 1 次 bootstrap，P95 < 300ms，支持 ETag / 304 |

### 6.2 可用性与容灾

- 目标可用性 99.9%；对局服务与 HTTP API 可分开部署、独立扩容。
- WS 多实例：Redis Pub/Sub 或网关做房间路由；同房间玩家尽量落同实例。
- 重启 / 滚动发布：对局状态落 Redis（含 TTL）或 DB；未开始的对局可取消并补偿报名费。
- PostgreSQL 主从 + 定期备份；Redis 排行榜/在线状态允许降级，
  但**钱包、订单、对局记录不能丢**。

### 6.3 一致性与幂等

- 钱包：余额 + 流水同事务；每条流水有 `balance_after`；定期对账 `sum(delta)` 与余额。
- 结算：三家 `gold_delta` 之和为 0；结算记录、钱包流水、任务/成就/排行榜更新
  要么全部成功，要么通过可靠事件补偿。
- 幂等键：购买、领奖、签到、结算、支付回调、出牌命令都需要。
- 乐观锁：钱包 `version`、设置 `version`、房间状态版本；冲突返回 `80003`。
- 订单：以 `order_no` 为业务主键，回调重复执行不重复发货。

### 6.4 安全、合规与反作弊

- **服务端权威**：所有规则、随机、结算在服务端；客户端只提交意图。
- **禁止客户端金额 / 价格 / 结果入账**：`amount`、`stake`、`price`、`gold_delta`。
- 令牌：JWT 强密钥；refresh 可轮换可吊销；设备会话可管理；`game_token` 只走服务端。
- 传输：全站 HTTPS / WSS；手机号、身份证 hash 脱敏。
- 防刷防重放：限流、幂等键、时间戳/nonce、验证码、风控评分。
- 反作弊：对局事件审计、异常胜率/串通检测、设备指纹、同 IP 多账号识别、牌局回放。
- 合规：**实名认证与防沉迷**（未成年人时长/消费限制）、隐私政策、
  **账号注销与数据删除接口**、内容安全（昵称/聊天/公告敏感词）、
  后台最小权限 + 金额变更二次确认 + 审计日志。

### 6.5 可观测性

- `request_id` 贯穿 HTTP / WS / 异步任务；结构化日志。
- 关键指标：QPS、P95/P99、错误率、WS 在线连接数、房间数、匹配时长、
  结算成功率、钱包流水异常数、支付回调失败数。
- 链路追踪：HTTP / WS / DB / Redis 关键路径。
- 告警：结算失败、**钱包负余额**、支付回调堆积、房间异常、
  配置发布失败、数据库/Redis 不可用。
- 按 `match_id` 还原事件流，支持客服与争议处理。

### 6.6 兼容性与发布

- API 版本 `/api/v1` 不变；**新增字段向后兼容，禁止删除或改变已有字段语义**。
- 配置版本独立于客户端版本；配置变更必须保证旧客户端可解析
  （未知字段忽略、枚举有默认值）。
- 请求头 `X-Client-Version` / `X-Client-Platform`；可对过旧版本强制升级。
- 灰度发布 + 可回滚。
- 本地存档 `user://profile.json` 可选择性上传迁移，不强制。

| 改造点 | 服务端需要提供的支撑 |

| 网络层 `ApiClient` | 稳定信封 + 明确错误码 + 401 语义（`10003`）能触发自动 refresh |
| 会话存储 | `access/refresh/game_token` 三件套；设备 ID 上报通道 |
| 资料与资产 | `GET /user/profile` 一次给全（避免客户端多次往返拼装） |
| 配置服务 | `config_version` + 内容哈希 + 304 支持 |
| 设置同步 | `PUT /user/settings` 部分更新 + `version` 乐观锁 |
| 对局改造 | WS `game.state` 作为**唯一重建依据**；`seq` 跳号检测 |
| 结算改造 | `game.finished` 返回 `balance_after`（客户端不再本地入账） |
| 签到/任务/成就 | 只发"领取意图"，结果以服务端返回为准 |
| 商城/皮肤 | 目录 + 拥有状态来自服务端；本地只缓存 |
| 消息中心 | `notifications` + `announcements` + `mail` 三源聚合 + WS 红点 |
| WS 客户端 | 首帧 auth、心跳、重连退避、`seq` 跳号、`game.sync` |
| 时间校准 | 服务端 `server_time` / `ts` |
| 隐私文案 | 服务端需提供"数据用途/注销"的说明口径 |

### 7.1 需求文档 §10.3 那 12 条"已知问题"，本项目的自查结论

这 12 条是**离线本地服务（`games`）里真实存在的缺陷**，而且客户端已经在按
（或绕着）这些形状写代码。因此逐条自查要回答的是两个问题：
**(a) 线上服务有没有同样的问题？(b) 如果线上修好了，两端行为不一致怎么办？**

| # | 离线服务（`games`）的问题 | 线上服务（本项目）现状 | 双端一致性处置 |
| --- | --- | --- | --- |
| 1 | 云存档 load 不返回正文 | **不适用**（线上不设云存档，资产以服务端为准） | 与客户端确认：迁移只走一次性脚本，还是需要 `cloud-save` 契约 |
| 2 | 下单金额由客户端传入 | **不存在此问题**：价格来自服务端目录，`/shop/purchase` 只收 `good_id` + 幂等键 | **线上必须守住**，不要为"对齐离线端"而接受客户端金额；离线服务侧应一并修（见 D-14） |
| 3 | 签到逻辑过于简单（无发奖/连签/周期/幂等） | **已正确实现**：7 天循环 + 连签 + 断签重置 + 钱包流水 + 唯一索引幂等 | 离线端需补齐同一套规则，否则同一玩家两种模式签到奖励不同 |
| 4 | WS `BroadcastToFriends` 实际广播给所有人 | **不存在此问题**：广播严格按房间座位投递，快照按座位裁剪 | **线上必须守住**（这是隐私问题）；离线端为单机场景，风险低但建议一并对齐 |
| 5 | WS 把收到的消息回显给自己 | **不存在此问题**：上行 op 与下行 type 分离 | 同上 |
| 6 | `GET /user/profile` 缺资产/战绩/设置 | **已有等价能力**，但路径为 `/user/me`、字段名与需求样例不同 | S0 契约对齐后两端统一为 `/user/profile` |
| 7 | 排行榜按 `game_id`，无法区分玩法 | **同样有此问题**：4 个全局榜，维度是"指标"而非"指标×玩法×周期" | 共同待办（RANK-01/02），两端一起扩维度 |
| 8 | 没有流水 / 余额版本 | **已解决**：`wallet_transactions` + 部分唯一索引幂等 + 用户行 `version` 乐观锁 | 离线模式若也要产出资产，需同样的账本结构才能合并 |
| 9 | 没有服务端对局状态机 | **已解决**：`internal/domain/game` 服务端权威状态机 + `internal/realtime` 房间 actor | 离线端是本地权威（本来如此）；关键是**结算口径必须一致**（同一套公式与倍数） |
| 10 | 没有幂等键机制 | **基本解决**：HTTP `Idempotency-Key` + 钱包幂等键；**WS `request_id` 尚缺** | WS 侧补齐（S2）；离线端为重试场景也要幂等 |
| 11 | 没有实名 / 防沉迷 | **同样缺失** | 共同待办 → S4；线上是合规硬门槛 |
| 12 | 客户端隐私文案写"本机不联网" | 客户端侧任务；线上需提供注销/删除能力 | S4；文案要改成"联网+离线双模式"的真实描述 |

### 7.2 离线模式带来的额外要求（需求文档未覆盖）

需求文档是在"未来要联网"的假设下写的，没有正面处理**离线模式长期存在**这件事。
本提炼补充三条：

| 要求 | 说明 | 落在哪个迭代 |
| --- | --- | --- |
| **契约 diff 不再是跨仓库动作，但要先有服务边界** | 客户端已并入 `apps/client`，契约文档与本地逻辑代码都在同一个仓库里；原先的跨仓库快照已删除。<br>而且 **`games` 并不是独立后端，它就是客户端里的本地逻辑** —— 只是它的**服务边界还不存在**（业务规则散在 `AppViewModel` 与 `PlayerProfile` 里），所以要先做 **C0** 把边界建起来 | **C0**（前置），之后每迭代执行 |
| **离线进度回传（范围已收窄）** | 依据 D-10 与 D-15，离线**不推进**任务 / 成就 / 签到，也**不产出金币**，因此回传只剩两件事：**离线战绩记录** + **少量积分**（有每日上限、不计入匹配分） | S1 |
| **离线不产出金币** | 金币只由联机模式产出 → 套利通道在定义上不存在，**不需要双币制、不需要分层结算**。这是"离线可玩"与"经济安全"之间最省的折中 | S1（仅 `offline_points` 记账 + 上限） |
| **无缝衔接** | 离线→在线不要求重新登录，靠长期设备凭证 `game_token` 承载（线上签发、离线保存并出示、`AUTH-06` 校验） | S1 |
| **结算口径一致性测试** | 同一副牌、同一操作序列，离线本地引擎与服务端引擎必须算出**同一个倍数与积分增减**。客户端已有约 15 个测试文件（`rules_smoke_test` / `mode_rules_test` / `result_ready_test` / `activity_shop_test` / `settings_test` 等）可直接作为对照基线 | S1 建立基线，S2 随对局协议扩展 |

> 第 3 条特别值得强调：本项目服务端的规则实现
> （`internal/domain/rules`，90 个用例）与客户端的本地引擎
> （`pattern_analyzer.gd` / `game_engine.gd`，客户端有 800+ 断言）**本来就是逐行对齐的**。
> 把"同一输入 → 同一输出"固化成跨端测试用例，是成本最低、收益最高的一致性保障。

## 9. 提炼结论：126 条需求可以归成 8 个工作包

把逐条端点按"工程上同一件事"归并，避免按 126 条散着排期：

| 工作包 | 覆盖需求 | 性质 | 主要风险 |
| --- | --- | --- | --- |
| **W1 契约对齐层** | 横向：信封 / 错误码 / 路径 / 分页 / 字段名 / **全链路 ULID** / WS 协议 | 改造（无新业务） | **双端可切换的前提**；一旦客户端按现状落地就改不动，必须最先做 |
